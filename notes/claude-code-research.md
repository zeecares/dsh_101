# Claude Code: Core Architecture vs. Extension Mechanisms — Primary-Source Research

Research for a tutorial comparing coding-agent architectures (Claude Code → pi → DeepSeek Harness).
All claims cite primary sources: [code.claude.com/docs](https://code.claude.com/docs/en/overview) (official Claude Code docs), [anthropic.com engineering](https://www.anthropic.com/engineering/claude-code-auto-mode), and [github.com/anthropics/claude-code](https://github.com/anthropics/claude-code). Docs fetched 2026; Claude Code was at v2.1.x (e.g. [CHANGELOG.md](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)).

## 1. Core architecture

### 1.1 The agentic loop

- Claude Code is a terminal agentic assistant; the docs describe the loop as three blended phases: **gather context → take action → verify results**, repeated until done, with the user able to interrupt at any point. ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works#the-agentic-loop))
- The docs define the architecture explicitly: *"Claude Code serves as the **agentic harness** around Claude: it provides the tools, context management, and execution environment that turn a language model into a capable coding agent."* ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works); [Glossary: "agentic harness"](https://code.claude.com/docs/en/glossary#agentic-harness))
- Loop mechanics confirmed at the implementation level by the Agent SDK docs (the SDK ships "the same tools, agent loop, and context management that power Claude Code" as a Python/TypeScript library): receive prompt → model evaluates and may request tool calls → SDK executes tools → results feed back → repeat until the model emits a response with no tool calls; each cycle is one "turn". ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview); [Agent SDK: how the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop))
- Context is a finite window: conversation history, file contents, tool outputs, CLAUDE.md, auto memory, loaded skills, and the system prompt share it; Claude Code auto-compacts when it fills, clearing older tool outputs first, then summarizing. ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works#the-context-window); [What survives compaction](https://code.claude.com/docs/en/context-window#what-survives-compaction))

### 1.2 Tools

- "Without tools, Claude can only respond with text." Built-in tools fall into five categories: **file operations** (read/edit/create/rename), **search** (glob/grep), **execution** (Bash, git, tests), **web** (WebSearch/WebFetch), and **code intelligence** (LSP-based, needs a plugin). There are also orchestration tools: spawning subagents (`Agent` tool), asking the user (`AskUserQuestion`), etc. ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works#tools); [Tools reference](https://code.claude.com/docs/en/tools-reference))
- **Bash execution**: each command runs in a separate process; environment variables do *not* persist between commands; aliases/functions from shell startup files are captured at session start; commands have a timeout (default 2 min, ceiling 10 min) and output is truncated (~30k chars inline, then a file path); long commands can be auto-backgrounded. ([Tools reference: Bash tool behavior](https://code.claude.com/docs/en/tools-reference#bash-tool-behavior))
- **Edit execution**: exact string replacement (`old_string` → `new_string`), no regex/fuzzy matching; three checks: read-before-edit, exact match, and uniqueness (or `replace_all: true`). ([Tools reference: Edit tool behavior](https://code.claude.com/docs/en/tools-reference#edit-tool-behavior))
- Checkpoints: before file edits Claude Code snapshots the files so `Esc` twice or `/rewind` can restore them; checkpoints are separate from git and can't cover external side effects (DBs, deploys). ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works#undo-changes-with-checkpoints); [Glossary: checkpoint](https://code.claude.com/docs/en/glossary#checkpoint))

### 1.3 Permissions

- Tiered permission system: **read-only** tools run freely inside the working directory; **Bash commands** prompt except a built-in read-only set (`ls`, `cat`, `git status`, …); **file modifications** prompt. "Permission rules are enforced by Claude Code, not by the model." ([Permissions](https://code.claude.com/docs/en/permissions#permission-system); [read-only commands](https://code.claude.com/docs/en/permissions#read-only-commands); [Security](https://code.claude.com/docs/en/security#permission-based-architecture))
- **Permission modes** (baseline, cycled with `Shift+Tab` or set via `--permission-mode` / `permissions.defaultMode`): `default` (a.k.a. Manual; reads only, everything else prompts), `acceptEdits` (auto-approves file edits + common fs commands like `mkdir`, `mv`, `cp`, `sed` in scope), `plan` (reads/explores, no source edits; presents a plan for approval), `auto` (a separate classifier model reviews actions in the background), `dontAsk` (auto-denies anything not pre-approved — for CI), `bypassPermissions` (`--dangerously-skip-permissions`; everything runs, isolated environments only). ([Permission modes](https://code.claude.com/docs/en/permission-modes#available-modes))
- **Auto mode** (2025–2026 addition): a *separate* classifier model (Sonnet 5 by default, server-configurable) reviews each action; it "never sees tool results, so injected instructions cannot influence its decisions"; blocked categories include `curl | bash`, production deploys, force pushes, `git reset --hard`, secret exfiltration, etc.; repeated blocks (3× consecutive / 20× total) fall back to prompting — thresholds are "not configurable". Classifier calls count toward token usage on API billing. ([Permission modes: auto mode](https://code.claude.com/docs/en/permission-modes#eliminate-prompts-with-auto-mode); [How we built Claude Code auto mode (Anthropic engineering blog)](https://www.anthropic.com/engineering/claude-code-auto-mode))
- **Fine-grained rules**: `permissions.allow` / `ask` / `deny` with `Tool(specifier)` syntax (e.g. `Bash(npm run build)`, `Read(./.env)`), evaluated deny → ask → allow, first match wins; a bare tool-name deny removes the tool from context entirely. ([Permissions](https://code.claude.com/docs/en/permissions#permission-rule-syntax))
- **Protected paths** (`.git`, `.claude`, `.mcp.json`, shell rc files, …) are never auto-approved except in `bypassPermissions`. ([Permission modes: protected paths](https://code.claude.com/docs/en/permission-modes#protected-paths))

### 1.4 Sandboxing (2025+)

- Built-in **sandboxed Bash tool**: OS-level filesystem + network isolation for Bash commands; uses macOS **Seatbelt** and Linux/WSL2 **bubblewrap + socat**; native Windows unsupported (use WSL2). Commands inside the sandbox can write only to the working directory + session temp dir; new network domains prompt. ([Sandboxing](https://code.claude.com/docs/en/sandboxing#get-started))
- Two sandbox modes: **auto-allow** (sandboxable commands run without prompting) vs **regular permissions** (all commands still go through the permission flow); there's an "unsandboxed retry" escape hatch for commands the sandbox can't run; `sandbox.failIfUnavailable` can make sandboxing a hard gate. ([Sandboxing: sandbox modes](https://code.claude.com/docs/en/sandboxing#sandbox-modes))
- Sandboxing is one layer of isolation; broader options: sandbox runtime (whole process incl. MCP/hooks), dev containers, custom containers, VMs, or Anthropic-hosted cloud VMs. ([Sandbox environments](https://code.claude.com/docs/en/sandbox-environments))

### 1.5 Sessions and environment

- Sessions are directory-tied; transcripts stored as plaintext JSONL under `~/.claude/projects/`; sessions can resume/fork; parallel sessions via git worktrees. ([How Claude Code works: sessions](https://code.claude.com/docs/en/how-claude-code-works#work-with-sessions))
- Execution environments: **local** (your machine), **cloud** (Anthropic-managed VMs or self-hosted), **remote control** (browser UI over a local process). ([How Claude Code works: environments](https://code.claude.com/docs/en/how-claude-code-works#execution-environments))

## 2. Extension mechanisms

The docs frame extensions as "a layer on top of the core agentic loop" ([How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works#tools)) and publish a decision map: "Extensions plug into different parts of the agentic loop" ([Extend Claude Code](https://code.claude.com/docs/en/features-overview#overview)).

### 2.1 CLAUDE.md memory files

- **What it does**: Markdown files of persistent instructions loaded at session start, in four scopes: managed policy (org path), user (`~/.claude/CLAUDE.md`), project (`./CLAUDE.md` or `./.claude/CLAUDE.md`), local (`./CLAUDE.local.md`); ancestor files load at launch, subdirectory files load lazily; `@path` imports (max depth 4); modular `.claude/rules/` with `paths:` frontmatter for path-scoped loading; `/init` generates one. ([Memory](https://code.claude.com/docs/en/memory#claude-md-files))
- **Auto memory**: Claude writes its own notes to `~/.claude/projects/<repo>/memory/`; the first 200 lines or 25 KB of `MEMORY.md` loads each session. ([Memory: auto memory](https://code.claude.com/docs/en/memory#auto-memory))
- **What it cannot do**: "CLAUDE.md content is delivered as a user message after the system prompt… there's no guarantee of strict compliance"; "Claude Code treats them as context, not enforced configuration." Enforcement belongs to hooks/settings. ([Memory](https://code.claude.com/docs/en/memory#troubleshoot-memory-issues); [Memory: CLAUDE.md vs auto memory](https://code.claude.com/docs/en/memory#claude-md-vs-auto-memory)) Mid-session edits to project-root/user CLAUDE.md **do not apply** until `/clear`, `/compact`, or restart (prompt-cache architecture). ([Prompt caching: editing CLAUDE.md mid-session](https://code.claude.com/docs/en/prompt-caching#editing-claude-md-mid-session))

### 2.2 Hooks

- **What it does**: user-defined handlers (shell command, HTTP endpoint, MCP tool call, LLM prompt, or subagent) that fire deterministically at lifecycle events — `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `UserPromptSubmit`, `SessionStart`, `Stop`, `SubagentStart/Stop`, `PreCompact`/`PostCompact`, `SessionEnd`, and more — configured under `hooks` in settings files. Hooks can **block** a tool call (exit 2, or `permissionDecision: "deny"`), **allow** it, inject context (`additionalContext`), rewrite tool input (`updatedInput`), or block a Stop. ([Hooks guide](https://code.claude.com/docs/en/hooks-guide#how-hooks-work); [Hooks reference](https://code.claude.com/docs/en/hooks#hook-events))
- `PreToolUse` hooks fire **before any permission-mode check in every mode**, so a deny can't be bypassed by switching modes — "hooks can tighten restrictions but not loosen them." ([Hooks guide: hooks and permission modes](https://code.claude.com/docs/en/hooks-guide#hooks-and-permission-modes))
- **What it cannot do** (documented limitations): command hooks "communicate through stdout, stderr, and exit codes only. They can't trigger `/` commands or tool calls"; `PostToolUse` hooks "can't undo actions since the tool has already executed" (they can append context or, with `decision: "block"` + `updatedToolOutput`, replace the output text, but the action already ran); async hooks "can't block or control Claude's behavior" — decision fields have no effect; a `Stop` hook that blocks 8× consecutively is overridden (cap via env var); per-hook timeouts (10 min default, 30 s for prompt hooks, 1.5 s budget for `SessionEnd`); parallel `PreToolUse` hooks rewriting input race non-deterministically. ([Hooks guide: limitations](https://code.claude.com/docs/en/hooks-guide#limitations); [Hooks reference: async hooks](https://code.claude.com/docs/en/hooks#run-hooks-in-the-background))
- Hooks run as external code (zero context cost unless they return output); they are not model-driven. ([Glossary: hook](https://code.claude.com/docs/en/glossary#hook); [Features overview: context cost by feature](https://code.claude.com/docs/en/features-overview#context-cost-by-feature))

### 2.3 MCP (Model Context Protocol)

- **What it does**: MCP servers add **tools, prompts, or resources** to Claude Code over an open standard protocol; configured via `claude mcp add`, `.mcp.json`, user/project scope, plugins, or claude.ai connectors. Local stdio servers run as child processes; remote HTTP/SSE/WebSocket supported. MCP **Tool Search** defers full tool schemas until use to save context. ([MCP](https://code.claude.com/docs/en/mcp); [Glossary: MCP](https://code.claude.com/docs/en/glossary#mcp-model-context-protocol))
- **What it cannot do**: MCP only adds *tools the model can call* — it does not change the loop, permissions, or the model itself; MCP tools still go through the normal permission flow (and orgs can force `ask` on connector tools); Anthropic "does not security-audit or manage any MCP server." ([Security: MCP](https://code.claude.com/docs/en/security#mcp-security); [MCP: organization controls](https://code.claude.com/docs/en/mcp#organization-controls-on-connector-tools))

### 2.4 Skills (SKILL.md)

- **What it does**: a directory with a required `SKILL.md` (YAML frontmatter + markdown instructions), optionally with supporting files, scripts, and templates. Skills are the successor to custom slash commands ("Custom commands → Skills" in the deprecated-terms table). Locations: enterprise (managed), personal `~/.claude/skills/`, project `.claude/skills/`, plugin `<plugin>/skills/`. Follows the **Agent Skills open standard**. ([Skills](https://code.claude.com/docs/en/skills#where-skills-live); [Glossary: skill](https://code.claude.com/docs/en/glossary#skill))
- **Progressive disclosure**: skill *descriptions* load at session start; *full content loads only when invoked* (`/name`) or when Claude judges it relevant — `disable-model-invocation: true` hides a skill until the user runs it. ([Features overview: context cost by feature](https://code.claude.com/docs/en/features-overview#context-cost-by-feature); [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works#manage-context-with-skills-and-subagents))
- Frontmatter can grant per-invocation `allowed-tools` (one-turn permission grants), restrict `disallowed-tools`, set `context: fork` to run the skill in a subagent, and accept `$ARGUMENTS`. Skills can inline shell output via `!` commands (dynamic context injection). Bundled skills (e.g. `/doctor`, `/code-review`, `/batch`) ship with Claude Code. ([Skills: frontmatter](https://code.claude.com/docs/en/skills#frontmatter-reference); [Skills: bundled skills](https://code.claude.com/docs/en/skills#bundled-skills))
- **What it cannot do**: a skill is instructions, not code — Claude interprets it, so outcomes vary ("Claude interprets the instructions; outcome can vary" vs a hook's guaranteed trigger); if a rule must hold every time, the docs say make it a hook, not a skill/CLAUDE.md line. ([Features overview: Hook vs Skill](https://code.claude.com/docs/en/features-overview#compare-similar-features))

### 2.5 Slash commands (.claude/commands/)

- Files in `.claude/commands/<name>.md` create `/name` commands; they support the same frontmatter as skills, but skills are "the recommended way" — "Skills are recommended since they support additional features like supporting files." A skill and a command with the same name: the skill wins. The term "slash commands" is deprecated in favor of "commands"/"skills." ([Glossary: command](https://code.claude.com/docs/en/glossary#command); [Skills: discovery](https://code.claude.com/docs/en/skills#where-skills-live); [Glossary: deprecated terms](https://code.claude.com/docs/en/glossary#deprecated-and-renamed-terms))

### 2.6 Subagents

- **What it does**: subagents are specialized assistants running in their **own context window** with a custom system prompt, tool allowlist, and permission mode; they return a summary to the parent. Built-in types: **Explore** (read-only research), **Plan** (read-only planning), **general-purpose**, plus helpers (`claude`, `statusline-setup`, `claude-code-guide`). Custom subagents are Markdown files with YAML frontmatter (`name`, `description`, `tools`, `model`, `permissionMode`, `skills`, `memory`, …) in `.claude/agents/` (project), `~/.claude/agents/` (user), managed settings, plugins, or passed as JSON with `--agents`. Subagents can preload skills, use hooks, maintain their own auto memory, and spawn nested subagents (depth limit). ([Subagents](https://code.claude.com/docs/en/sub-agents); [Glossary: subagent](https://code.claude.com/docs/en/glossary#subagent))
- `claude --subagent` is **not** a current flag; the CLI reference documents `--agents` (define subagents via JSON) and `--bg --agent` (run a named subagent as a background session). ([CLI reference](https://code.claude.com/docs/en/cli-reference#cli-flags))
- **What it cannot do**: subagents don't inherit the parent's conversation history; the main session's auto memory isn't loaded into them (except forks); built-in Explore/Plan skip CLAUDE.md; background subagents get a reduced built-in tool set; `AskUserQuestion` and `EndConversation` are removed from all subagents. ([Subagents: available tools](https://code.claude.com/docs/en/sub-agents#available-tools); [Subagents: what loads at startup](https://code.claude.com/docs/en/sub-agents#what-loads-at-startup))

### 2.7 Plugins (yes, they exist now)

- **What it does**: plugins are the packaging layer — "a bundle of skills, hooks, subagents, and MCP servers packaged as a single installable unit," with an optional `.claude-plugin/plugin.json` manifest (`name`, `description`, `version`, `author`). A plugin can contain `skills/`, `commands/`, `agents/`, `hooks/` (`hooks.json`), `.mcp.json`, `.lsp.json` (code-intelligence LSP servers), `monitors/`, `bin/` (PATH additions), and default `settings.json`. Plugin skills are **namespaced** (`/plugin-name:skill-name`) to avoid collisions. ([Plugins](https://code.claude.com/docs/en/plugins); [Glossary: plugin](https://code.claude.com/docs/en/glossary#plugin))
- **Distribution**: plugins install from **marketplaces** — the official Anthropic marketplace (`claude-plugins-official`), the community marketplace, or org/self-hosted marketplaces; versioned releases (`version` field gates updates); orgs can constrain versions and recommend plugins. ([Discover plugins](https://code.claude.com/docs/en/discover-plugins); [Plugin marketplaces](https://code.claude.com/docs/en/plugin-marketplaces); [Plugin dependencies](https://code.claude.com/docs/en/plugin-dependencies))
- **Relationship to skills**: not "Agent Skills vs plugins" — plugins *bundle* skills (plus agents/hooks/MCP). "Skills are the most flexible extension"; "Plugins are the packaging layer." A skill folder with a `.claude-plugin/plugin.json` loads as a plugin (`<name>@skills-dir`). ([Features overview](https://code.claude.com/docs/en/features-overview#overview); [Skills: skills-directory plugins](https://code.claude.com/docs/en/skills#where-skills-live))
- **What it cannot do**: plugins are configuration bundles — they cannot add new permission modes, new hook events, or modify the agent loop; `hooks/` in a plugin still runs within the documented hook contract; the repo's own plugins (e.g. `security-guidance`, `code-review`) are implemented as skills+hooks+MCP over the existing surface. ([Plugins reference](https://code.claude.com/docs/en/plugins-reference); [github.com/anthropics/claude-code/plugins](https://github.com/anthropics/claude-code/tree/main/plugins))

## 3. Where the seams are: what Claude Code cannot do

Evidence-based limits from primary sources:

1. **The kernel is closed-source and Anthropic-versioned.** The GitHub repo `anthropics/claude-code` hosts README, CHANGELOG, example hooks/settings, and official plugins — but no kernel source. Its license is "© Anthropic PBC. All rights reserved. Use is subject to Anthropic's Commercial Terms of Service." ([LICENSE.md](https://github.com/anthropics/claude-code/blob/main/LICENSE.md); [README](https://github.com/anthropics/claude-code/blob/main/README.md)) The npm package ships a compiled binary; versions are Anthropic-released (`2.1.x` in [CHANGELOG.md](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)).
2. **You cannot modify the agent loop in the CLI.** The loop, context management, and tool execution live inside the closed harness. The only sanctioned way to get the loop as *your* code is the **Agent SDK**, which exposes "the same tools, agent loop, and context management" as a Python/TypeScript library (those SDK repos are open source) — that is a different product surface, not a change to the CLI kernel. ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview); [Agent SDK: modifying system prompts](https://code.claude.com/docs/en/agent-sdk/modifying-system-prompts))
3. **You cannot hot-load a new permission model.** The set of permission modes is fixed (`default/acceptEdits/plan/auto/dontAsk/bypassPermissions`); you can switch modes at runtime or set defaults, but not define new ones. Rule evaluation order (deny→ask→allow) and the auto-mode classifier (Anthropic-configurable model, non-configurable block thresholds) are built-in. ([Permission modes](https://code.claude.com/docs/en/permission-modes); [Permissions](https://code.claude.com/docs/en/permissions#manage-permissions))
4. **Core settings changes are not hot-reloaded.** Because of prompt caching, editing CLAUDE.md or the output style mid-session "doesn't apply" until `/clear`, `/compact`, or restart; the system prompt is Anthropic's ("Core instructions… You never see it" in the context-window timeline). ([Prompt caching](https://code.claude.com/docs/en/prompt-caching#actions-that-keep-the-cache); [Context window](https://code.claude.com/docs/en/context-window))
5. **Hooks are deliberately bounded.** They cannot trigger `/` commands or tool calls; async hooks cannot control the loop; `PostToolUse` cannot undo an executed action; `Stop` hooks are force-overridden after 8 consecutive blocks; some events can't be blocked at all (`SessionStart`, `Setup`); hooks can tighten permissions but never loosen them past deny/ask rules; `EndConversation` cannot be removed by deny rules while any other tool remains. ([Hooks guide: limitations](https://code.claude.com/docs/en/hooks-guide#limitations); [Hooks guide: hooks and permission modes](https://code.claude.com/docs/en/hooks-guide#hooks-and-permission-modes); [Tools reference: EndConversation](https://code.claude.com/docs/en/tools-reference#endconversation-tool-behavior))
6. **CLAUDE.md and skills are advisory, not enforced.** "Permission rules are enforced by Claude Code, not by the model"; CLAUDE.md is delivered as a user message with "no guarantee of strict compliance." ([Permissions](https://code.claude.com/docs/en/permissions#permission-system); [Memory](https://code.claude.com/docs/en/memory#troubleshoot-memory-issues))
7. **Model and safety layers are Anthropic-controlled.** Auto mode requires specific Anthropic models (Sonnet 5 / Opus 4.7+ on most providers) and a server-side probe that scans tool results; `bypassPermissions` refuses to run as root/sudo; certain tools (e.g. `EndConversation`) only exist under Anthropic-defined conditions. ([Permission modes](https://code.claude.com/docs/en/permission-modes#eliminate-prompts-with-auto-mode); [How we built Claude Code auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode))
8. **`--bare` mode proves the extension stack is separable**: it "starts without loading hooks, skills, plugins, MCP servers, auto memory, or CLAUDE.md" — i.e. the extensions sit on top of a fixed core, not inside it. ([Glossary: bare mode](https://code.claude.com/docs/en/glossary#bare-mode))

## 4. Ecosystem reality: usage model and billing

- **Usage model**: most surfaces require a **Claude subscription** (Pro/Max/Team/Enterprise via claude.ai) **or an Anthropic Console (API) account**; the terminal CLI also supports third-party providers (Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry). Providers differ in billing and feature availability (e.g. web sessions, Remote Control, routines require a claude.ai account). ([Overview](https://code.claude.com/docs/en/overview); [Admin setup: choose your API provider](https://code.claude.com/docs/en/admin-setup#choose-your-api-provider))
- **Official pricing posture**: the docs do *not* state a fixed per-session price. They publish enterprise averages: "around **$13 per developer per active day** and **$150–250 per developer per month**, with costs remaining below $30 per active day for 90% of users." The `/usage` example shows a local estimate of **$0.55** for one session's token usage, computed at list rates ("doesn't reflect promotional pricing or contracted discounts"). ([Costs](https://code.claude.com/docs/en/costs); [Costs: /usage](https://code.claude.com/docs/en/costs#using-the-usage-command))
- **Billing paths**: subscriptions meter against a per-seat rolling allowance (Team/Enterprise) or usage credits past plan limits; Console/API usage is billed per token in workspaces with spend limits; cloud-provider deployments bill through AWS Marketplace / cloud consoles; gateways let orgs route all traffic through one provider credential billed at API rates. ([Costs: manage costs for your organization](https://code.claude.com/docs/en/costs#manage-costs-for-your-organization); [Gateways](https://code.claude.com/docs/en/gateways); [Claude Platform on AWS](https://code.claude.com/docs/en/claude-platform-on-aws))
- **Data usage**: commercial users (Team/Enterprise/API): Anthropic does **not** train models on Claude Code prompts/code by default (opt-in Development Partner Program only); standard retention 30 days (Zero Data Retention available for qualified Enterprise); consumer users control training opt-in (30-day vs 5-year retention). Sessions are stored locally as plaintext JSONL under `~/.claude/projects/` (30 days default). ([Data usage](https://code.claude.com/docs/en/data-usage); [How Claude Code works: sessions](https://code.claude.com/docs/en/how-claude-code-works#work-with-sessions))
